# Карта воронки CRM и её варианты

## 1.1. Карта воронки («Карта проекта»)

Горизонтальный ряд колонок-стадий (swimlane). Внутри колонки — роботы, задания, условия, паузы, смена стадии. Провальные стадии — узкие красные колонки справа, успех — зелёная.

Все колонки — внутри родительского swimlane-«шапки» воронки (оранжевый, см. [styles.md](styles.md)).

### Цвета блоков

| Вид | Смысл | Цвет |
|-----|-------|------|
| Колонка стадии | обычная стадия | swimlane без заливки |
| Успех | финальная «хорошая» стадия | зелёный |
| Провал | отказ / брак | красный |
| Задание человеку | «Запрос дополнительной информации» (+ «с отклонением») | зелёный |
| Задача | активити «Задача» / дело | зелёный |
| Действие системы | поля, списки, пауза, письмо… | белый |
| Смена стадии | «Сменить стадию» | жёлтый |
| Запуск БП / вебхук / активити приложения | подпроцесс, REST, код | фиолетовый |
| Событие / триггер / уведомление | внешнее событие, уведомление | фиолетовый |
| Условие | развилка да / нет / N веток | ромб |
| Заметка | пояснение | серое облако |
| Отключённый робот | в Битрикс выключен | серый, подпись «отключено» |
| Автозадача | устаревший блок | **не использовать** в новых схемах |

### Тексты блоков

- **Задание человеку** — строками:
  `Запрос дополнительной информации` (жирным) / `Заголовок:` / `Заполняют сотрудники:` / `Название задания:` / `Описание задания:` (если есть) / `Поля` списком / `Кнопки:` через « / » / `Показывать поле ввода комментария: Да|Нет` / `Обязательность комментария: Да|Нет` / `Тип делегирования:` (по умолчанию «Только подчиненным»).
  Кнопки по умолчанию: «Готово»; с отклонением — «Согласовано / Не согласовано».
- **Задача** — название активити жирным + **только заполненные** поля (название, постановщик, ответственный, описание, приоритет, флаги). Без кнопок, комментария, делегирования — это не задание БП.
- **Действие** — название + строки «настройка — значение» только для заполненных параметров. Полные параметры («Новый ответственный = …», условия полей, тексты SMS) пиши целиком, не сокращай до «Изменить поля».
- **Незнакомое активити** — белый блок: название типа + «настройка — значение». Не подписывать «Активити приложения».
- Служебные, но значимые активити **не пропускать**: «Получить информацию о привязанном элементе» (с типом родителя: сделка / лид), «Получить информацию об элементе CRM», «Получить данные CRM», «Получить информацию о сотруднике», «Прерывание процесса».

### Размеры

- «Толстая» стадия с ветками / петлями — ~680–860 px, подгонять под содержимое.
- Обычная стадия — ~300–340 px.
- Провал — ~120–150 px.
- Блок действия — ширина 280, ромб 88×88, зазор между блоками ~22.

### Развилки

- N веток — веер в стороны; подпись живой ветки на стрелке.
- **Пустая ветка** — заглушку не рисуем: одна подписанная стрелка от ромба к следующему блоку по обходному рельсу. Рельс ставится **за внешней границей всего поддерева** развилки, не рядом с ромбом — иначе режет вложенные ветки.
- Если развилка завершает логику стадии — живую и пустую ветви сводим в невидимую конечную точку.
- Развилка «одна живая + одна пустая» — колонки разнесены минимум на ширину ромба; этот зазор учитывается в ширине всего поддерева.
- Ромб без действий в ветках — не рисуем.
- Одна живая ветка без пустых соседей — просто продолжение вниз.
- Сторона выхода в N-way: ветка левее центра ромба → левая вершина, иначе правая (две стрелки из одной вершины не тянуть).

## 1.1a. Схема на доработку (для инженера-настройщика)

Карта 1.1 в **итоговом** виде: видно, что уже настроено и что инженеру изменить. Делается по пометкам заказчика на существующей карте.

1. Всё, что **уже настроено**, — обычными цветами 1.1.
2. Всё **новое или изменённое** — **красным**: блоки, ромбы, заметки, обязательные поля.
3. **Новая стадия** — красная колонка с **толстой рамкой** (strokeWidth=3). Провальные стадии тоже красные, но с тонкой рамкой — не путать.
4. **Настроено сейчас, нужно удалить** — не выбрасывать: блок красным пунктиром с зачёркнутым текстом, заголовок «Удалить: …», в описании — куда перенесено.
5. Существующий блок, в котором изменилась часть (добавилось обязательное поле, другая целевая стадия), — красный, в тексте явно **что именно** изменилось.
6. Не «улучшать» настроенную логику, которую заказчик не помечал (не объединять одинаковые ветки и т. п.) — иначе инженер переделает работающее.
7. Неясные места — красное облако с «⚠» и общий список **«Открытые вопросы»** на схеме. Своё толкование пометки — тоже туда, чтобы заказчик подтвердил.
8. Обязательная **легенда**: красное = добавить / изменить, пунктир зачёркнутый = удалить, остальное = уже настроено.

Пометки «изменить» / «удалить» сильнее любого другого цвета блока.

## 1.1b. Связи между воронками (сделка ↔ смарт-процесс)

Две воронки на одном листе и стрелки, что и когда передаётся между ними.

1. Связанную воронку ставить **под** стадией, из которой создаётся её элемент (первая стадия СП — прямо под стадией-источником).
2. Каждая связь — стрелка **от стадии к стадии** с номером в кружке (①, ②…). Новые связи — красные (§1.1a); пунктир — предложение или вопрос к заказчику.
3. Стрелки идут в промежутке между воронками, у каждой свой горизонтальный уровень и свои точки выхода / входа на грани стадии — не сливаются и не режут блоки.
4. Рядом — таблица **«Связи»**: №, Когда (стадия / событие), Откуда → куда, Что передаём (поля «куда = откуда»), Чем настроить (какой робот / БП), На что обратить внимание.
5. В таблице обязательно: условие создания элемента, защита от дубля, кто ответственный, обязательные поля стадии-источника, сопоставление списков, защита от петель (робот одной воронки не запускает обратный робот другой), что происходит с элементом СП, если сделка ушла в провал.

Доработка существующего листа: сдвинуть пул СП, добавить стрелки и таблицу — остальные элементы листа не трогать.

## 1.3. Карта роботов стадий

Визуально как 1.1, источник — реальные роботы и триггеры на стадиях портала («Роботы и триггеры»).

- Если на стадии включён дизайнер БП — рисовать дерево активити с развилками, а не плоский список.
- Выражения `{=Variable:…}`, `{=Document:…}`, константы → русские названия.
- Значения списков (hash / XML_ID) → подписи вариантов.
- Стрелки внутри стадии — короткие углы у блоков, **без** рельса на край широкой колонки.

## 1.5. Черновик стадий (если схему генерируют из данных)

Удобно сначала описать логику без координат, потом рисовать:

```json
{
  "funnel": [
    {
      "name": "Название стадии",
      "blocks": [
        { "kind": "assignment|task|action|event|condition|block|note|bp", "text": "..." }
      ],
      "success": false,
      "changed": false
    }
  ],
  "failStages": [{ "name": "Провал", "blocks": [] }]
}
```

- `condition` с N ветками: `branches: [{ "label": "...", "blocks": [] }]`.
- Пометки доработки для любого блока и стадии: `"changed": true` (красный), `"removed": true` (красный пунктир, зачёркнуто).

## 1.6. Каркас воронки

Только колонки стадий без наполнения — быстрый снимок структуры. Дальше наполняется роботами (1.3) или БП (1.2).
